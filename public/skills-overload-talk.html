Where we’re going · The whole picture

This is a domain-specific harness.

Here is the destination first: a persona made of teams, goals that choose the work, connectors to real data, a vault for credentials, custom apps, and a person who approves what matters.

It looks like a lot. It is built from one small thing: the box marked Agent skill, inside the playbook. That is the smallest unit of agent work today. Let’s zoom in.

The problem · One skill

It starts with one skill.

A skill is a folder an agent can load: instructions in SKILL.md, sometimes reference files, sometimes scripts. It follows the open Agent Skills format, which more than 70 agent platforms now read.

One skill is easy. You wrote it, you know what it does, you trust it.

Source: Anthropic, Donating Agent Skills to the Agentic AI Foundation, 22 Oct 2026

0:15 to 0:30. Keep it simple. Instructions, maybe references, maybe scripts. One skill, you trust it.

The problem · Skills overload

Every client keeps its own pile.

Claude Code reads ~/.claude/skills and CLAUDE.md. Codex reads .agents/skills and AGENTS.md. Cursor has .cursor/skills and its rules. Grok CLI reads .agents/skills too. Every engineer runs a different mix.

So the same pr-review skill gets copied into every folder, then edited in one. Everyone rebuilds the same thing, nobody can find what works, and none of it adds up to an agent the whole team can rely on.

Sources: Claude Code skills · Codex skills · Cursor skills · grok-cli

0:30 to 0:55. Ask: hands up if you use more than one of these clients. Keep it up if you know which copy of your pr-review skill ran this morning.

The problem · The public pile

The public pile is bigger still.

When Anthropic handed Agent Skills to the Agentic AI Foundation in October, it counted 1 million published skills and nearly 280 million installs. Many arrive the same way: one install command pulls a GitHub repo and copies it into the folder of every agent on your machine.

Nobody can tell you how many of those fit your domain. Or which ones are safe to run.

Sources: Anthropic, 22 Oct 2026 · skills CLI

0:55 to 1:10. One million skills, 280 million installs. Then the turn: which of those fit your domain, and which are safe?

The problem · Trust

You can’t see what a skill will run.

Researchers confirmed 157 malicious skills among 98,380. One reads like a harmless calculator; line 32 of its Python script opens a reverse shell. Snyk found a critical issue in 13.4% of 3,984 public skills.

Even the scanners disagree. Marketplace checks flagged anywhere from 6.0% to 46.8% as malicious; with repository context, only 0.52% stayed suspicious. Whose verdict do you trust? Someone else’s scanner can’t be the answer.

Sources: Liu et al., arXiv 2602.06547 (USENIX Security 2026) · Snyk ToxicSkills, Feb 2026 · Holzbauer et al., arXiv 2603.16572

1:10 to 1:35. The calculator is the moment. The SKILL.md looks safe, the script is not. Then: the scanners can’t agree with each other. Trust has to come from your own review, and it has to stay fixed once you have reviewed it.

How it happened · The unpinned layer

We locked every layer except the skills.

Models go through a gateway with budgets and rules. Tools are declared in config and pinned to a version. Skills, the layer that steers the agent most directly, still arrive from a URL with no version and no review.

An instruction in a SKILL.md steers the agent, but nothing holds it in place. Without a pin and a review, nobody can say which instructions the agent followed yesterday. That is why agents stall before production.

1:35 to 1:55. Most teams already have controls on models and tools. Skills are the gap. Point at the dashed Skills layer.

The solution · 1. Playbook

Keep the skill. Give it a contract.

The spec starts with a playbook: the reusable unit a team can share. It declares inputs, steps, outputs, connector operations and approval rules. The skill inside stays a plain Agent Skills folder.

Its steps declare the capabilities they need, and the workspace binds them at run time. The next team reuses the same definition without rewiring anything.

1:55 to 2:15. From here we build up, smallest first. The skill doesn’t change. It gets a contract around it.

The solution · 2. Package

Ship it like a dependency.

A playbook is published as an npm archive. Whoever uses it pins four things: registry, scoped name, exact version and a SHA-512 integrity digest. The harness verifies the pin before it accepts the package.

External skills are pinned the same way, by full Git commit or npm release plus a content digest. Bundled scripts run only from declared entry points, isolated, with network and credentials switched off.

Spec: Packaging and installation · Portable playbooks

2:15 to 2:40. This is the heart of it. The hash proves sameness, not safety. Your review gives safety; the pin stops it drifting.

The solution · 3. Team

Group playbooks into a team.

A team owns its goals, its playbook placements and its spending limits. Each placement pins an exact release, so a new version of a playbook changes nothing until the team reviews and adopts it.

A coordinator skill decides which playbooks run, and in what order. A good one says: use the fewest playbooks that meet the criteria, and ask for missing inputs instead of guessing.

2:40 to 2:55. The coordinator line comes from a real team SKILL.md in my implementation, but keep it generic here.

The solution · 4. Persona

Compose teams into a persona.

A persona brings teams together around one domain model, so they agree on what the organisation’s data means. It pins every team by exact version and digest.

That is the idea in one line: the persona is the lockfile for your agents. Pick it up and you get exactly the reviewed skills everyone else on the team has.

2:55 to 3:15. Say the line slowly: the persona is the lockfile for your agents.

The solution · 5. Goal

The goal chooses the work. A person approves the plan.

Create a goal inside a team. The coordinator plans which playbooks to invoke, in the order their dependencies need. With plan review on, the proposed tasks wait for a person before anything runs.

If the plan reveals a missing capability, the team drafts a new playbook, reviews it and registers it. Drafting it grants no access.

3:15 to 3:35. Point at the board: two of three playbooks chosen, nothing ran until approval.

The solution · 6. Governed execution

Rehearse the change. Then approve it.

When a goal needs to change live data, the playbook drafts the action and the harness rehearses it in a sandbox with live effects off. A domain specialist approves the exact action.

The harness rechecks before dispatch and records a receipt. Corrections feed the next reviewed revision, so the expert’s feedback is no longer lost.

3:35 to 3:50. Corrections no longer get lost: they become the next reviewed revision.

The solution · Connect the dots

Now the whole picture reads.

A skill inside a playbook. Playbooks pinned into teams. Teams pinned into a persona. Goals pick the work, and a person approves the plan and every protected action. Connectors move the data, the vault holds the keys, and the harness binds whichever model fits.

It is the same board as the first screen. Every box now has a job, and every box has a version.

3:50 to 4:05. Pause on this. Same picture as the start, and now they can read it.

The solution · 7. Software factory

Your coding agent builds the harness.

Keep Claude Code, Codex, Cursor or Grok CLI. Point it at the spec’s llms.txt and let it draft playbooks and evals; you review them and publish each with an exact pin. The persona’s root SKILL.md follows the Agent Skills format, so any skills-compatible client can read its instructions.

Start with coding: the pr-review, release-notes and deploy-check skills from that pile become reviewed playbooks in a software delivery persona. Swap the domain and the same factory builds a persona for forms, customs or banking.

Open problem · Goals over time

What I haven’t solved: goals that change.
